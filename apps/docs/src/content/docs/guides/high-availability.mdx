Truss talks to Postgres over a single `DATABASE_URL`. That means **HA is a property
of the Postgres you point it at**, not of Truss itself, which is exactly what you
want: use whatever database high-availability story you already trust.

## What the default deployment gives you

Both shipped deployments run a **single Postgres instance**:

- **Docker Compose** (`docker-compose.selfhosted.yml`) , one `postgres` container.
- **Helm chart** (`charts/truss`) , one Postgres `StatefulSet`, `replicas: 1`.

This is deliberate: it runs anywhere, it's cheap, and it's the right default for a
homelab, a single VPS, or an evaluation. It has **no failover**, if that Postgres
goes down, Truss is down until it comes back. Take regular backups (see
[Branching & Backups](/guides/branching/)).

:::note
Setting `replicas: 2` on the default StatefulSet does **not** give you HA , it's a
plain StatefulSet, not a replication-aware operator. For real HA use one of the
options below.
:::

## Option 1 , managed Postgres (recommended for most)

The simplest path: don't self-manage HA at all. Point `DATABASE_URL` at a managed
Postgres (Amazon RDS / Aurora, Cloud SQL, Neon, Supabase, Crunchy Bridge). They
handle replication, automatic failover, backups, and PITR for you.

```bash
DATABASE_URL=postgres://user:pass@your-managed-host:5432/truss?sslmode=require
```

Nothing else in Truss changes. This is the least operational burden and the safest
choice unless you specifically want to run the database yourself.

## Option 2 , run Postgres under an operator (self-managed HA)

If you want HA on your own Kubernetes cluster, run Postgres under a replication
operator such as [CloudNativePG](https://cloudnative-pg.io) (CNPG) and point
`DATABASE_URL` at the operator's read-write Service. CNPG gives you streaming
replicas and **operator-driven automatic failover** with no extra tooling.

```yaml
# a CloudNativePG Cluster (NOT the Truss chart), e.g. instances: 3
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: truss-postgres
spec:
  instances: 3        # 1 primary + 2 streaming replicas
```

CNPG then manages three Services , `*-rw` (primary, use this in `DATABASE_URL`),
`*-ro` (replicas), `*-r` (any). It also pairs cleanly with a PgBouncer `Pooler`
(`type: rw`), which follows the primary automatically.

### What failover does

If the primary becomes unhealthy, the operator:

1. **Promotes** the most up-to-date replica to primary.
2. **Repoints the `-rw` Service** at the new primary automatically.
3. **Rejoins** the old primary as a replica once it recovers.

Because Truss and any pooler connect through the `-rw` Service (not a pod), they
follow the new primary with **no config change** , a brief blip during promotion,
then reconnect.

### Async vs sync replicas

Replication is **asynchronous** by default: fast, but a failover can lose the last
few transactions that hadn't reached the promoted replica (a small RPO window). For
**zero data loss**, require a synchronous replica (trades a little write latency):

```yaml
spec:
  instances: 3
  postgresql:
    synchronous:
      method: any
      number: 1     # at least one replica must confirm each commit
```

:::caution[Replicas on one node are not fault tolerance]
Running all instances on a **single node** gives you the failover mechanism and read
scaling, but not real HA , if the node dies, every copy dies with it. Real HA needs
instances spread across **separate nodes / availability zones**.
:::

:::note[Failover is tuned for safety, not speed]
CNPG waits to confirm the primary is genuinely unhealthy before promoting, and lets
a gracefully-stopped primary drain first, so a clean shutdown can take longer to
fail over than a hard crash. Tune `failoverDelay` / `switchoverDelay` if you need
faster promotion.
:::

## Option 3 — Operator-managed HA

The [Truss operator](https://github.com/binarysquadd/truss) wires all three tiers of HA from a
single `TrussInstance` custom resource, so you don't hand-assemble the CNPG cluster, the app
Deployments, and the disruption budgets yourself.

### Managed Postgres HA

Set `dependencies.postgres.mode: managed` and the operator provisions a CloudNativePG cluster
for you — the same streaming-replica + automatic-failover setup as Option 2, without authoring
the `Cluster` manifest. The instance count follows the app-tier `scaling.profile`:

```yaml
apiVersion: apps.truss.binarysquad.org/v1beta1
kind: TrussInstance
metadata:
  name: truss
spec:
  scaling:
    profile: medium        # dev → 1 instance; medium / large → a 3-instance HA cluster
  dependencies:
    postgres:
      mode: managed        # operator provisions a CloudNativePG cluster
```

The `dev` profile gets a single Postgres instance; `medium` and `large` get a 3-instance HA
cluster. Pair it with `spec.backup.enabled` for CNPG scheduled backups and PITR.

### App-tier HA

Scale and protect the API and dashboard tiers directly on the CR:

```yaml
spec:
  components:
    api:
      replicas: 3
    dashboard:
      replicas: 3
  resilience:
    pdb: {}               # a PodDisruptionBudget per component
    topologySpread: true  # spread pods across zones / nodes
```

`components.{api,dashboard}.replicas` set the pod counts, `resilience.pdb` adds a
PodDisruptionBudget per component so voluntary disruptions can't take a tier down, and
`resilience.topologySpread` spreads pods across zones and nodes.

### The operator itself runs HA

The operator Deployment ships with **2 replicas and leader election**, so one replica is always
active while the other stands by, plus its own PodDisruptionBudget (`minAvailable: 1`). A node
drain or a single pod failure never leaves your `TrussInstance` resources unreconciled.
